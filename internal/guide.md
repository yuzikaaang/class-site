## 1. 日常：改完东西怎么上线

**你不用做任何操作。** 按站规，AI 每次改完会按顺序做完这些：

| 步骤 | 说明 | 你要做什么 |
|---|---|---|
| ① 改代码 | `index.html` / `games/*.html` / `sw.js` | 提需求 |
| ② 本地测试 | 起本地服务 + 自动化测试，不能只靠「看代码觉得没问题」 | — |
| ③ 同步文档 | 站内公告（如有用户可见变更）+ `internal/notes.md` | — |
| ④ 推送 Gitee | **先 `git fetch` + `git rebase` 拉最新，再 `commit + push`** 到 `zikang0529/class-site` 的 `master` | — |
| ⑤ 主链更新 | Gitee 镜像**自动**同步到 GitHub Pages | — |
| ⑥ 备用链接 | AI 重新发布 WorkBuddy 链接 | — |
| ⑦ 你验收 | 打开链接看一眼 | ✅ **这步是你的** |

> 主链一般 **1~5 分钟**内刷新。超过 15 分钟没变，才需要到 Gitee 仓库「管理 → 仓库镜像管理」手动点一次同步。

> ### ⚠️ 多 AI 协作铁律（2026-08-30 立，见 `internal/notes.md` 站规「多 AI 同步」）
> 你可能会同时给多个 AI（比如 A 和 B）改这个仓库。**远端是唯一真相源，每个 AI 本地只是副本。**
> - **动手前必拉**：`git fetch <HTTPS带令牌地址> master` → `git rebase FETCH_HEAD`，把别的 AI 推的新提交接在本地改动之前，再编辑。
> - **绝对禁止 `git push --force`**：那会把别的 AI 的提交整个覆盖掉，数据直接没了。推送被拒（`! [rejected] (fetch first)`）是正常的，先 `fetch`+`rebase` 再看，别强推。
> - **同会话比跨会话危险**：会话还活着时，AI 本地文件是某天别的 AI 推送前的旧版，不拉就改就会撞冲突；新开对话工作区自动重新拉取、反而是最新的。
> - 推送前用 `git status -sb` 确认没有 `ahead`/`behind` 之外的分叉即可。

## 2. 凭据管理：Gitee access token 轮换

### 2.1 现在的推送方式（2026-08-30 起，已不用 SSH）

推送走 **HTTPS + access token**，不配置 SSH 公钥。你只需要：

1. 把 Gitee 令牌发给 AI **一次**（见 2.4）
2. AI 存本地，每次推送直接复用

> **唯一注意**：Gitee 镜像同步到 GitHub 用的是 **GitHub 的 token**（在 Gitee 仓库「管理 → 仓库镜像管理」里配置），和你的 Gitee 令牌是两回事，别混淆、别误删。

### 2.2 令牌过期 / 想换新的 / 怀疑泄露了怎么办

1. 打开 `https://gitee.com/profile/personal_access_tokens`
2. 点 **生成新令牌**
3. 描述随便填，比如 `class-site-2026-09`
4. **权限勾选：只勾需要的。** 单纯推代码勾 **`projects`（仓库读写）** 就够，**不要全选**——尤其别勾 `删除仓库` 之类危险的
5. 点提交 → **立刻复制那串令牌**（关掉页面就再也看不到了，只能重建）
6. 把**旧的那条删除**
7. 把新令牌发给 AI（附上老规矩：存本地、不上传、用完提醒你删聊天记录）

> **别怕换**：仓库内容不受任何影响，令牌只是「开门的钥匙」。30 秒的事，不放心就换。

### 2.3 （历史）SSH 公钥 —— 已弃用，不用再管

2026-08-30 之前 AI 是用 SSH 公钥推送的。**这个方案已经废弃**，你账号上如果还挂着 title 为 `class-site-sandbox-2026...` 的旧公钥，**删掉即可**（不影响现在的令牌推送）；不删也无害。

> **当年踩过的坑（2026-08-30 留档）**：删掉正在用的公钥 = 正在干活的 AI 立刻失去推送能力（`Permission denied (publickey)`），且沙箱里的私钥随会话消失、换会话就要重配——所以当年每次换 AI 都要重新配 key，非常麻烦，这也是后来改令牌方案的原因。**这条已是历史，别再按它操作。**

### 2.4 令牌到底放哪？（2026-08-30 你拍板的方案：**不加密、不入库、你自己存**）

你想过三个方案，对比如下：

| 方案 | 做法 | 优点 | 致命问题 |
|---|---|---|---|
| ① 每个 AI 单独配 SSH 公钥 | 换一个 AI 就加一次 key | 令牌从不离开你手里 | 换 AI 就要重配，**麻烦**；而且沙箱密钥是临时的，换个会话也要重配 |
| ② 令牌加密后存进仓库，密钥交给 AI 解密 | 一次配置，所有 AI 通用 | 省事，不怕忘 | **等于没加密**：密文在仓库里、密钥也在仓库里，任何拿到仓库的人都能当场解开，只比明文多一层纸。而且**密钥一旦发给 AI 就进了聊天记录**，令牌明文同样暴露 |
| ③ **令牌自己存备忘录，需要时发给 AI**（✅ 你选的） | 仓库里什么都不留 | **仓库零泄露面**；忘了也能去平台重建；不怕换 AI | 换新 AI 时要粘贴一次（就几秒） |

**结论：走方案③。仓库里不放任何令牌、不放密文、不放加密脚本、不放密钥。**

**你只需要发一次（2026-08-30 已发过）**：

1. 打开备忘录 → 复制令牌
2. 发给 AI，附一句：**「这个令牌就存你的本地，每次直接用就行，但是不要上传」**
3. 发完 → **删掉这条聊天记录**
4. 之后 AI 会把令牌存在**本地工作区**（仓库外），每次推送直接复用，**不会再找你要**

> **记住这两点**：
> - **AI 的「本地」是临时的** —— 沙箱会话一结束，存令牌的文件跟着消失。所以**换新 AI 或新会话时，你需要再发一次**。
> - **你的备忘录是唯一长期副本** —— 别删。忘了也没关系，去 `https://gitee.com/profile/personal_access_tokens` 删掉重建即可。

> **省事小技巧**：让 AI 用 HTTPS 地址推，令牌直接拼在命令里（`https://用户名:令牌@gitee.com/zikang0529/class-site.git`），
> **别让它 `git remote set-url` 写进 `.git/config`** —— 那样令牌会落到磁盘上。用完 `remote` 保持原样（SSH 地址）不用管。

给 AI 的规矩（这段会写进 3.3 的开场白，新 AI 一接手就知道）：

- **不主动索要令牌**，等站主发（站主发过一次后，就存在本地直接复用）
- 收到后**只存本地工作区（仓库外）**，不写进代码、文档、注释、`commit message`、日志
- **绝不把令牌上传**：不 commit 进仓库、不 push 到任何远程、不写进 README
- 汇报时**不回显令牌**，也不要说「令牌已收到，前四位是 xxxx」这种话
- 干完活**主动提醒站主删聊天记录**（站主直发令牌的那一条）
- **本地文件随会话消失** —— 换新会话时主动告诉站主「令牌文件没了，需要重发一次」

### 2.5 万一删错了怎么办

| 误删的东西 | 后果 | 怎么救 |
|---|---|---|
| ~~SSH 公钥~~（已弃用） | 无 —— 现在推送不靠它 | 不用救 |
| access token | 推送不了 | 重新生成一个（见 2.2），**旧 token 无法恢复，只能重建**，再发给 AI 一次 |
| GitHub 的 token（镜像同步用） | 主链不再自动更新 | 去 GitHub 重建 token，回 Gitee「仓库镜像管理」里更新认证 |

**仓库代码本身不会丢** —— 令牌和密钥都只是「开门的钥匙」，删了不影响仓库里的内容。

## 3. 接入一个新的 AI

这是本文件最值钱的一节。换 AI 时你最烦的就是「重新交代一遍」，照下面做就行。

### 3.0 当前工作方式（2026-08-30 起：只有一种）

**令牌直发** —— 你把 Gitee 令牌发给 AI **一次**，AI 存本地、每次推送直接复用（详见 2.4）。没有别的模式可选，不用考虑配公钥。

> 换新 AI / 新会话时，只需要把令牌**再发一次**（老 AI 的本地文件随会话消失了），附一句 **「存本地、不上传、用完提醒我删聊天记录」**。
> 历史模式（SSH 常驻授权 / 用后即删 / 不授权）**已全部弃用**，不用再了解。

### 3.1 三条原则

1. **给权限，不给密码。** AI 需要的是「能推代码」，不是「能登录你的账号」。推代码用 Gitee 令牌就够了。
2. **先让它读文档，再让它动手。** 新 AI 最大的问题不是能力，是**没有上下文**。不读 `internal/notes.md` 就动手，等于让一个刚来的同学改你们班的规矩。
3. **要求它区分「验过」和「没验过」。** AI 很容易含糊地说「已完成」，实际有些东西它压根访问不到（比如本环境连不上 GitHub）。

### 3.2 权限分档（可以把这张表直接发给新 AI）

| 档位 | 事项 | AI 该怎么做 |
|---|---|---|
| 🟢 **可直接做** | 改代码、跑测试、`commit + push` 到 Gitee、重新发布备用链接、改 `internal/` 里的文档 | 做完报告即可，不用先问 |
| 🟡 **做完要说明** | 改站内公告文案、改站规/铁律、动学生数据（清空排期、删券记录）、改对外可见的链接 | 可以做，但必须明确列出改了什么、影响谁 |
| 🔴 **必须先问** | 动你的账号设置（Gitee/GitHub/Vercel）、轮换或删除凭据、删库或回滚版本、改点歌平台的 CORS 白名单 | **先问，你点头再做** |

**它主动索要时，直接拒绝**：

- Gitee / GitHub 的**账号密码**
- 点歌平台的 **API key 明文**（页面里存的是混淆密文、运行时才解密，这个设计必须保持）
- 导出备份包的**解压密码**（连位数都别告诉它）

**令牌可以给，但规矩是**（见 2.4，方案③）：

- 只在你主动要用的时候发，**它不能主动要**；发**一次**就够，AI 会存本地复用
- 发完**删聊天记录**；心里不踏实就去删掉重建
- 它必须做到：**只存本地工作区（仓库外）、绝不把令牌上传**（不入库、不 push、不写进任何文档/注释/日志）、不回显、不写进 `commit message`、干完提醒你删

每次让 AI 改完，让它按这个格式汇报。如果它只说「已完成」，就追问一句「哪些是实测过的？哪些你访问不到？」

4. 确认 `internal/notes.md` 最后一条更新记录写完整了 —— **下一位 AI 全靠它接手**

## 4. 其他常见操作

### 4.1 换域名后要加 CORS 白名单

点歌平台是**你自己的 fork 仓库 `yuzikaaang/VoiceHub`**，白名单**硬编码**在源码里（没有环境变量可配）：

1. 打开 `yuzikaaang/VoiceHub` → 文件 `server/middleware/api-0-open-cors.ts`
2. 在 `ALLOWED_ORIGINS` 这个 Set 里加一行，例如 `'https://新域名'`
3. 提交到 `main` 分支 → Vercel 自动部署

**匹配规则（已实测）**：精确匹配 **协议 + 主机 + 端口**，**末尾不能带斜杠**。

验证是否生效（不用浏览器，一条命令）：

```bash
curl -i -X OPTIONS 'https://xsyzc2505.dpdns.org/api/open/songs' \
  -H 'Origin: https://你的域名' \
  -H 'Access-Control-Request-Method: GET' \
  -H 'Access-Control-Request-Headers: x-api-key'
```

看到 `access-control-allow-origin: https://你的域名` 就是成功了。

### 4.2 `secrets.json.enc`（历史遗留文件，已不再使用）

> ⚠️ 仓库根目录的 `secrets.json.enc` 是**早期版本**把令牌加密存仓库的遗留物。**2026-08-30 起令牌改为站主直发、不入库（见 2.4），这个文件已经没用**，放着不碍事，不用管它。
>
> 旧文档里写的 `./scripts/decrypt-secret.sh` 和 `secrets-hint.txt` **早已删除**，别再找了。
>
> 如果某天真要读它：文件是 OpenSSL 加密的二进制密文，密码是**你自己设的**（**位数不写进任何文档** —— 写「6 位数字」这种提示等于帮别人把暴力破解范围直接缩小到 100 万种，2026-08-27 那次事故的成因就是这个）；让 AI 现场写命令解密，**密码你自己输、不要让 AI 记录明文**。忘了密码：里面的内容都可以去各自平台重新生成，**不影响站点运行**。

### 4.3 备份与还原

- **备份**：站点「数据管理 → 导出备份」，会存一份到浏览器下载
- **仓库快照**：`class-site-backup.zip`（每次改完 AI 会重打；**不含** `internal/`）
- **还原**：在 Gitee 上找到对应提交 → 回滚；或让 AI 从 `backup/` 目录里找历史包

### 4.4 备用链接失效了

沙箱会话结束后链接可能失效。让 AI 重新发布一次即可（站规：push 后自动重发，不用你开口要）。

## 5. 出问题速查

| 现象 | 大概率原因 | 怎么办 |
|---|---|---|
| 主链内容没更新 | 镜像同步延迟 | 等 5 分钟；超时去 Gitee「仓库镜像管理」手动同步 |
| 备用链接打不开 | 沙箱会话结束 | 让 AI 重新发布 |
| 备用链接在微信里白屏 | 微信内置浏览器限制 | 复制链接到系统浏览器打开 |
| 抽签提示「连不上点歌平台」 | CORS 白名单没配、或 API 真挂了 | 见 4.1；主链正常就说明是备用域名没加白名单 |
| 备份包下载失败（`.zip` 403） | 备用域名前置 WAF **按后缀封禁 `.zip`** | 站点已内置回退（会自动取无扩展名副本），重试即可 |
| AI 说推不了代码（`401 / 403 / Authentication failed`） | 令牌过期 / 被删了 | 去 Gitee 重建令牌（见 2.2），再发给 AI 一次 |
| AI 改完了但没推送成功 | 上面同一原因 | 改动**没丢**，只是滞留在本地。换好令牌后一次性推送即可 |
| 换了个 AI / 新会话 | — | 把 Gitee 令牌**再发一次**（见 2.4），AI 存本地后直接复用，发完删聊天记录 |
| 令牌发给 AI 了，事后不放心 | — | 去 Gitee 删掉重建（30 秒），**仓库内容不受任何影响** |
| 忘了 `secrets.json.enc` 的密码 | — | 无所谓，那个文件已弃用（见 4.2），令牌都能去各自平台重建，站点照常运行 |
| 页面显示旧内容 | Service Worker 缓存 | 硬刷新；SW 是网络优先，一般自动更新 |
